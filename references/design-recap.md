# 设计与决策讨论的补充规则

适用于产品、服务、流程、界面或机制设计讨论。目标是让读者理解方案、取舍和当前状态；演示只是解释手段，不扩展为实现完整产品的任务。

## 还原决策

- 区分参考对象、当前现状、候选方案、参与者偏好、明确决定和未决问题。不要用自己的设计判断替换参与者的选择。
- 识别讨论的收束过程。保留仍有效的约束，淘汰已被明确否定的方案；只有局部变更时，不删除其他已定要求。
- 保持承诺强度。“必须”“优先”“可以”“最好”“暂不做”不能相互替换；明确决定也不能被泛化成含糊倾向。
- 将机制、资源、范围和下一步组织成便于理解的主题，而非逐句复制对话。版本范围与分工只记录材料支持的内容，不编造负责人、优先级或时间表。
- 如有必要，用简短状态看板收口。看板应索引决定与剩余问题，而不是再次完整复述正文。

## 选择演示的尺度

- 对位置和布局，用空间示意；对流程和依赖，用连接关系；对多种形态，用同一条件下的对照。先保留关系，再追求视觉相似。
- 当操作本身是理解方案的关键时，考虑提供能实际操作的局部演示。若静态图已足够，不为增加按钮而开发交互。
- 选择能体现核心机制的最小状态集合。演示用的实体、数量与操作由当前材料决定，不继承任何测试用例的配置。
- 将已确定的规则与演示假设分开。缺少参数时可以只演示确定的状态关系；不得把演示设定写成产品决定。
- 被讨论产品的布局和行为约束属于示意中的产品，不自动成为整份纪要的页面要求。

## 交互实现与验收

- 先明确初始状态、用户动作、状态变化和反馈。可见标签、几何位置与计算结果必须一致。
- 根据机制需要提供撤销、重置或退出；重复触发和边界状态不能造成不合理累积或无法恢复的界面。
- 使用语义化控件，支持键盘、可见焦点与必要的状态播报。弹层可关闭，退出后恢复合理焦点。
- 对动画提供减少动态效果的替代方式，保留等效操作能力。示意不得触发真实业务行为。
- JavaScript 不可用时，主要内容、规则与限制仍可阅读，不让关键事实只存在于交互结果中。
- 实际操作主要状态与边界情况；测量几何变化时等待过渡完成。内容正确、视觉清楚和操作有效需要分别检查。
