# 产品与游戏设计讨论：把方案展示出来

当输入是产品设计、游戏机制、UI/UX、版本范围讨论时读取。总结仍是纪要，不是开发用户谈到的完整游戏，也不把全部页面改成产品演示。保留任务与约束，在关键处用小型可体验的示意帮助读者理解。

## 先按主题整合，再判断状态

- 长讨论通常以 3–5 个大分部容纳多个小节，例如设定/地图与关卡/成长与经济/MVP，或数值/结算/适配与风格/封板范围；按实际材料调整。不要把所有细节压进五张同构短卡，也不要照搬科普的“难点→原理→未来感受”。
- 保留需求的限定：必须、最好、比如、暂定、先不做分别代表不同强度。区分“竞品有”“本作没做”“倾向”“最终决定”，不能把引用竞品当作本作已实现。
- 说话人有改口时以最后明确决定收束，同时保留影响实现的变化。例如奖励从奖牌/道具讨论到照片，可收束成“照片”；从做饭小游戏收敛为先用现有玩法的难关，不得又把独立小游戏列成 MVP 必做。
- 对亲历的项目现状、明确会议决定，不套“未独立核验”新闻免责声明。对未识别的发言者不编姓名与负责人，不把某人提议写成双方共识。外部断言保留归属。
- 尾部用简洁的“已定/待定”或“本版/后续”看板及真实下一步收口。任务要具体，但不擅自新增工期、优先级、负责人或排期。若原文只说有趣，不能直接断言“明确延后”。

## 让图形承担信息

| 材料关系 | 展示方式 | 必须保留的语义 |
|---|---|---|
| 人物、载具、场景 | 内联 SVG 的小场景或人物组合 | 人物可辨识、气氛符合输入；不是几个孤立 emoji |
| 旅行路线、关卡节点 | 一张有起点、路径、节点、标记的地图 | 明确行进方向、周期节点、单线/自由路线区别；具体排序未知则标“示意” |
| 周期奖励与积累 | 一组短流程 + 回环箭头 + 可点开的纪念物样例 | 奖励去向、累积如何留下；样例不是已发生的真实记录 |
| 多种货币或资源 | 分栏对照来源/用途/限制 | 不混淆金币、星星、体力；未定数值不补造 |
| 成长链与缺口 | 主链 + 汇入箭头/缺口插槽 | 不把每日奖励误画成等级之后的另一个线性阶段 |
| 横竖屏适配 | 宽背景中嵌中央竖屏 UI 的空间图 | 哪部分延展、哪部分保持尺寸、哪些页面例外；不能只写原则 |
| 抽屉/全屏菜单 | 同一示意视口内的形态切换 | 改变面板几何与位置，不只是按钮变色或换一行说明 |
| 纯色/立体 UI 风格 | 少量按钮/面板实物风格对照 | 展示风格区别，同时说明已定方向与个人倾向 |

图表、示意与交互均用带五项证据属性的 figure 包裹。source 选支持主要关系的一段准确原话；示意性补充在图注就近说明。不从原版 output.html 复制它可能误读的事实。

## 有用且克制的交互

材料明确谈到“点开照片”“完成目标领奖”“两种菜单形态”“截停倍率”时，优先制作对应的小演示，而不是全部退化成文字或条形图。选择足以说明核心机制的交互，避免开发整款游戏。

- **照片预览**：CSS/SVG 绘制 2–3 张旅途插图，明确“示例，正式内容待定”。原生 button 打开 dialog，关闭按钮、Esc 和遮罩可关闭，关闭后焦点返回触发按钮。图片内容由题材合理示意，不伪称真实成果。无 JS 时缩略图和说明仍可见。
- **目标完成**：点击三项目标可切换完成，全部完成才发一次额外奖励；撤销/重置后移除奖励，不能重复累计。数值模糊时，展示完成数和原文明确的全勤奖励，基础档位注明待核对，不编造固定总经验。若演示必须用假设数值，紧邻标明示例假设，不把它写进决定清单。
- **菜单形态**：原生按钮 + aria-pressed 同步状态，用不同面板宽度/定位展示侧边抽屉与全屏，内容始终可辨认。示意只占纪要的一块区域，不遮盖整个页面。
- **倍率截停**：仅在原文讨论此机制时提供开始/截停/重置；倍率和指针位置对应，标签声明区间边界为演示设定。不实际播放广告、不给出真实奖励。开启 prefers-reduced-motion 时改为手动选择/步进，不能留下无法操作的指针。
- 静态人物/载具与装饰不必不停动。动画与状态变化帮助理解机制即可；键盘可操作，按钮有可见焦点，状态提示用 aria-live。

## 保持阅读节奏

- 核心地图或空间图应成为视觉焦点，不只在一排小图标中象征性出现。旁边短文解释限制，图下不重复整段流程。
- 卡片样式可以统一，内部结构要随语义变化：地图、循环、资源对照、交互面板、范围看板交替出现。不要给所有节点机械加编号。
- 不把第一组医药样本的绿色和药丸固定成通用品牌。旅行题材可用暖色田园，纸牌收尾可用清爽蓝绿；在深色模式仍有清楚层级。
- 页面讲解的“产品只延展背景、UI居中”等要求适用于图中的产品，不自动成为纪要本身的网页布局规则。

## 交付验收

对照输入审查最终决定、暂缓范围、数字口径和关系方向。浏览器中实际点击/撤销/重置每个机制，检查移动端与深浅色、弹窗关闭、重复操作和无 JS 回退。原版只是风格基准，不要求复刻其数值误读或未经来源支持的决策。明确记录未完成的检查。

### 生成后必须纠正的偏差

- 不代替参与者做产品设计。原文对多次弹板的评价是“虽有干扰但可接受，先照竞品录屏做”，不能改写成“已决定只用一个结算板”。写明参考作流程、本作现状、实际下一步，别把模型的 UX 偏好放进“已定”。
- 讨论末尾明确“那你就先做每日目标”，就记录为先做，不降格成“倾向”；同样，不把地图中的“小狗最好可见”升级为必须。
- “暂不设计完整数值”不等于删除已经确定的资源用途；广告翻倍金币不能因为前面说过“先只收星星”就被全盘延后。
- 设计输入的核心交互不是可有可无的装饰。材料围绕照片点开、每日目标反馈、菜单切换展开时，成品至少实际演示这些相应动作。不能只画三个目标的静态卡片就声称展示了完成机制。
- 旅途设计应有能看见人物/载具的场景或路线图，以及可点开的示例照片；路线行进方向必须与原文一致。小游戏的早期想法和 MVP 采用的现有玩法难关要分清。
- 交付前回读输入末尾的决定，再反查正文与范围看板；保留原文明确的最终要求，不随意添“更好的做法”。
- 修订时不要把评审话术写进成品标题，例如“不把多块反馈改写成单板”“不编700总数”。用直接面向读者的标题与简短限定，说明产品本身。
- 对空间交互，图形位置、可见标签和 JS 计算必须一致；原文“正中两倍”就把 2× 放在中央，不能按数值从小到大排列而改变机制。所有可点元素都要能用键盘完成同一动作，不能只给外层控制按钮加键盘支持。
- 修订已有 HTML 后再次检查 share-cover、字面引文、title/h1 等完整性，避免修好正文却删掉非可见交付结构。
- 并列资源用对照布局，不用箭头串成“星星→金币→广告”这种原文不存在的转化链；箭头必须有真实的因果、流转或顺序含义。
- 已明确“第5关难关”时保留这个位置，其余易/中顺序未定则只标数量。不要为避免臆测反而把已定位置也写成未知。
- 图表来源优先选支持核心关系的完整单句/连续段落，不拼接改写。验证时注意 HTML 属性会规范化换行；不要依靠多段拼接充当字面引文。
